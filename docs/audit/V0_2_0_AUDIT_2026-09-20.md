# v0.2.0 pre-release crate audit

**Date:** September 20, 2026
**Against:** candle-mi `0.1.24`, `candle-core`/`candle-nn` 0.11.0, stable `rustc` 1.98.0,
MSRV toolchain `1.91`, Windows 11
**Purpose:** establish, before any v0.2.0 code lands, what is actually wrong with the crate, so the
release scope is chosen from evidence rather than from the feature request that triggered it.

Every finding below was reproduced directly. Where a number came from a survey rather than a
command, it is labelled as such.

## Finding 1 (Critical): generic interventions are silently ignored on three backends

`HookSpec::intervene` is honoured by `GenericTransformer`, `GenericMdlm` and `OthelloGpt`. It is
**not** honoured by:

- **`GenericRwkv`** at any point except `Embed`. `src/rwkv/mod.rs` contains 7 `is_captured` calls
  and exactly **1** `interventions_at` (line 1668, `Embed`). `ResidPre`, `ResidPost`, `RwkvState`,
  `RwkvDecay` and `FinalNorm` are capture-only.
- **`StoicheiaRnn` and `StoicheiaTransformer`** at any point at all. `src/stoicheia/mod.rs`
  contains 10 `is_captured` calls and **zero** occurrences of `interventions_at` or
  `apply_intervention`.

RWKV's separate state-intervention mechanism (`state_knockout`, `intervention_positions`) does work
and is correctly documented in `HOOKS.md` as a distinct path. This finding concerns only the
generic tensor-level path.

**Why this is Critical rather than a papercut.** `BACKENDS.md:573` already lists
"`Intervention::Zero` at `ResidPost(0)` changes the output (proves hooks are wired)" as a backend
conformance requirement, and three backends fail it without erroring. In an interpretability crate
the consequence is specific and bad: a causal experiment against `GenericRwkv` returns the
unmodified baseline, the measured effect is zero, and the researcher concludes there is no causal
effect. The instrument reports a null that is an artifact of the instrument. This is the same class
as `backward()` succeeding while training 1 parameter in 29
(`docs/dogfooding-feedbacks/trainable-backbones.md` section 2), which was treated as
silent-wrong-answer severity and fixed in v0.1.20.

## Finding 2 (High): two RUSTSEC advisories, both fixed in this commit

`cargo audit` against the `0.1.24` lockfile:

| crate | was | advisory | required | now |
|---|---|---|---|---|
| `h2` | 0.4.15 | RUSTSEC-2026-0258, unbounded empty DATA frames | >= 0.4.16 | **0.4.19** |
| `rustls` | 0.23.41 | RUSTSEC-2026-0285, TLS 1.3 handshake messages accepted across encryption level boundaries (CVSS 5.3) | >= 0.23.45 | **0.23.45** |

Both arrive transitively through `reqwest`/`hyper`, i.e. through the `hf-hub` download path.
`cargo audit` is now clean; the two remaining entries (`instant`, `paste`, both unmaintained) are
pre-existing allowed warnings.

**One trap worth recording.** A plain `cargo update -p rustls` moves it only to 0.23.43 and prints
"available: v0.23.45". That is **not** an MSRV constraint: `rustls` 0.23.45 declares
`rust-version = "1.71"`, far below this crate's 1.91. The blocker is that reaching 0.23.45 also
requires moving the sibling `rustls-webpki` 0.103.13 -> 0.103.15, which a single-package update will
not do. `cargo update -p rustls --precise 0.23.45` moves both. Anyone re-running the advisory fix
should expect the same and not conclude the MSRV is in the way.

**MSRV verified, not assumed.** `cargo +1.91 build --no-default-features --features transformer`
(the lane CI actually runs) exits 0 with the new lockfile.

## Finding 3 (High): CI clippy never lints tests or examples

All 13 clippy lanes in `.github/workflows/ci.yml` take the form

    cargo clippy --no-default-features --features <X> -- -W clippy::pedantic

with **no `--all-targets`**. Clippy therefore sees the library only. Test and example targets are
compiled by CI (`cargo test ... --test validate_stoicheia`, line 73) but never linted.

78 lint errors have accumulated in that blind spot, all of them violations of lints the crate sets
to deny (`expect_used`, `indexing_slicing`):

| file | errors |
|---|---|
| `tests/validate_stoicheia.rs` | 51 |
| `examples/attention_routing.rs` | 20 |
| `examples/steering_convergence.rs` | 2 |
| `tests/bench_hook_diagnostic.rs` | 1 |

None of these files carries a file-level `#![allow(...)]`, so they are genuine violations rather
than deliberate exemptions. Reproduce with a feature set that compiles them plus `--all-targets`.

**Resolved.** The full count with every feature enabled is 81 errors across 9 files, not the 78
across 4 that the stoicheia-only lane showed.

The crate already has a settled convention here, which decided the treatment: 30 files under
`tests/` and `examples/` allow `unwrap_used` and `expect_used`, 43 allow `indexing_slicing`, 28
allow `panic`. The failing files were not exceptions to a rule, they were simply missing the header.
Each gained exactly the lints it needs rather than a blanket list.

Two were fixed rather than exempted, where the lint was pointing at something real:

- `parse_clt_feature` (`examples/steering_convergence.rs`) collected into a `Vec` and indexed
  `[0]`/`[1]` behind a length check. It now takes `splitn(2, ':')` and destructures two `Option`s,
  which drops the allocation and matches `CONVENTIONS.md`'s "prefer `.get(i)` with explicit error
  handling".
- The rank-3 projection check in `tests/validate_stoicheia.rs` looped over `0..batch` and indexed;
  it now iterates with `enumerate`, removing both the range loop and the indexing.

One genuine clippy contradiction had to be waived explicitly. The GPU-lane guard in both
`bench_hook_*` tests asserts on a `cfg!`: `assertions_on_constants` rejects
`assert!(!cfg!(feature = "cuda"))` because the condition folds at compile time, and `manual_assert`
rejects the equivalent `if`/`panic!` because it wants the assert back. The condition genuinely is a
compile-time constant, so one lint must be waived; `manual_assert` is waived at the statement, with
the reasoning recorded inline.

`--all-targets` was added to all 11 CI clippy lanes, which is the part that prevents recurrence, and
each lane was verified locally before the change. `cargo clippy --all-targets -- -D warnings` now
passes across every feature except `metal` (finding 4).

## Finding 4 (Medium): the documented pre-commit ritual is not runnable anywhere

`CLAUDE.md` prescribes `cargo clippy --all-targets --all-features -- -D warnings` before every
commit. On Windows that command cannot succeed: `--all-features` enables `metal`, which pulls
`objc2-metal` and `objc2-foundation`, which do not build on a non-Apple target. The failure is
`error: could not compile objc2`.

**Corrected 2026-09-20, after the question "would WSL help?" was asked.** It would not, and the
first version of this finding understated the problem by blaming Windows. Neither `objc2-metal` nor
`objc2-foundation` is target-gated in `candle-core`'s manifest, so Linux fails identically and WSL
reproduces the same error. Worse, `--all-features` also enables `cuda`, which pulls `cudarc`: a Mac
can build `metal` but not `cuda`, and everything else can build `cuda` but not `metal`. **The
command is unbuildable on any single machine in existence**, not merely on this one. Nothing in the
repo ever ran it: no CI workflow and no `preflight.ps1` step uses `--all-features`, and the two
places that mention it (`ci.yml:199`, `scripts/preflight.ps1:103`) are comments explaining why
per-feature lanes are used instead.

This is structural and pre-existing, not introduced by the lockfile change above (`git diff
Cargo.lock` touches neither `objc2` nor `metal`, and plain `cargo tree -i objc2` prints nothing,
confirming it is not a host-target dependency).

The wider Metal picture uncovered while checking this -- that candle-mi has no `metal`-gated code of
its own, that nothing has ever compiled the feature, and that `select_device` cannot return a Metal
device -- is recorded in [`docs/metal-preflight.md`](../metal-preflight.md), together with the
decision to defer it until a local Mac is available.

The runnable equivalent on Windows is every feature except `metal`:

    cargo clippy --all-targets --features "cuda,transformer,mmap,rwkv,rwkv-tokenizer,diffusion,clt,sae,stoicheia,quantized,memory,probing,training" -- -D warnings

`CLAUDE.md` should say so, otherwise the instruction reads as followed-and-green when it was never
executable.

## Finding 5 (Medium): struct-level semver exposure

From a full survey of the public API (enumerated, but the counts below are survey output, not a
single reproducible command):

- The crate has **zero `builder()` methods** (`grep "fn builder" src/` is empty). This is a
  reproducible fact.
- 33 `#[non_exhaustive]` attributes exist, all but two on enums. The **enum** policy is fully
  satisfied, including the one documented `// EXHAUSTIVE:` exception, and a new enum since the
  2026-07-01 audit (`FoldPath`, `src/optim.rs:655`) correctly takes that path.
- **Struct** exposure is where the gap sits: config structs parsed from `config.json` grow fields
  release over release (`TransformerConfig` has 29 public fields and has demonstrably accreted
  `o_proj_bias`, `use_qk_norm`, `qk_norm_eps`, `bidirectional`), and each addition is technically a
  breaking change for external struct-literal construction.
- `DOSE_LEVELS: [f32; 6]` (`src/interp/steering.rs:21`) leaks its length into the public type;
  every sibling constant in the crate already uses `&[..]`.

Addressed by v0.2.0 item 4. The ordering constraint there is real: `TransformerConfig`'s only
public construction path today is `from_hf_config`, so marking it `#[non_exhaustive]` without
adding `Default` or a builder in the same release removes external construction entirely rather
than merely restricting it.

## Semver baseline

`cargo-semver-checks` 0.50.0 installed and a baseline captured before any API change:

    cargo semver-checks check-release --baseline-version 0.1.24 \
        --only-explicit-features --features transformer

    Checking candle-mi v0.1.24 -> v0.1.24 (no change; assume minor)
    Checked [0.039s] 196 checks: 196 pass, 58 skip
    Summary no semver update required

This confirms the tool runs against this crate and that the working tree is API-identical to
published `0.1.24`, so every break reported later in v0.2.0 is attributable to v0.2.0 work rather
than to drift already sitting on `main`. The 58 skips are checks that do not apply to this crate's
item kinds, not silent failures.

Re-run the same command after item 4 and make the CHANGELOG's breaking-change list match its
output, rather than hand-deriving it from the diff.
